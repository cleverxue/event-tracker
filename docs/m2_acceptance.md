## 三、实现要点（对照规格 5.2）

1. **拉取**：`hisAnnouncement/query` 逐只翻页（pageSize=30，含发布当天），
   orgid 映射缓存 1 天；失败降级跳过该组并记日志，不阻塞。
2. **状态机**：回购 planned→in_progress→completed/terminated；
   增持 planned→in_progress→completed/failed；协议转让 agreed→approved→
   completed/terminated。状态只进不退、终态粘滞；终态记录 status 置
   completed/terminated（增持 failed 记 terminated，timeline 保留 failed）。
3. **均价回填**：进展/完成类公告下载正文 → 抽取累计股数与累计金额 →
   `avg_price = 金额 / 股数`，`avg_price_source` 记来源公告 ID（规格 5.2
   唯一均价实现路径）。已回填后，M4 偏离度优先用 avg_price（规格十-5）。
4. **并发**：watchlist/timeline 写走 `app/storage/store.py` 的 Lock +
   临时文件原子替换；管线可重复跑（timeline 按
   (event_id, announcement_id, state_after) 去重）。

## 五、过程中发现并修复的三个数据质量问题（均有回归固化）

1. **完成公告漏分类（影响 146 行 watchlist）**：completed 阶段正则原先要求
   家族词与完成词连续（"增持计划实施完成"），"回购方案**实施完成**"
   "增持股份计划实施完成"这类插字标题整类漏匹配，完成公告冒充 initial
   混入 watchlist、状态机永远停在 planned。修为家族无关关键词（家族词由
   门禁保证），重建 watchlist 2183 → 2037 行，M1 抽检复跑仍全绿。
2. **跨事件公告混入**：同族多事件时，事件 B 的扫描看到了事件 A 公告日
   之前的公告（timeline 出现倒序行）。补"公告日期 ≥ 事件公告日"约束。
3. **多受让方分笔金额算错均价**：过户公告含"转让总价 3.24 亿 + 四个受让方
   分笔 226M/57M/19M/21.6M"，取最后一笔会把均价算低 15 倍。改为：单值直接
   用；多值优先"合计/总额/总价"限定值；仍无法区分则**放弃回填**（宁缺毋滥，
   错误偏离度会产生虚假信号）。

## 六、与规格的差异 / 边界（最简方案，均已标注）

1. **同族多事件统一推进**：同一股票同一事件族的多条事件无法从标题可靠归属，
   按"同族统一推进"处理（仍受"公告日期 ≥ 事件公告日"约束），均价取各事件
   自己扫描到的最新进展公告计算值（规格未覆盖）。
2. **triggered 记录仍跟踪进展**：规格 5.2 字面为 watching；triggered 事件的
   后续演化对复盘有价值，故一并处理（不改写触发状态）。
3. **timeline 记录全部命中公告**：含状态未变的进展公告（state_before ==
   state_after），便于前端展示公告节奏；规格字面为"状态迁移写入 timeline"。
4. **expired 由 21:30 任务标记**：跟踪窗口过期且仍 watching 的记录置 expired
   （规格 4.1 有该状态但未指定标记时机）。
5. **均价在进展类与完成类公告上都会回填**：完成公告的累计总数是最权威来源；
   仅当能同时抽到累计股数+金额时才回填，公告直接载明"成交均价"但无累计量
   时不回填（规格指定 avg = 金额/股数为唯一路径）。
6. **多值不一致放弃回填**：见第五节第 3 条，规格未覆盖。
7. `publish_timestamp` 精度取决于巨潮接口：实测 `hisAnnouncement/query`
   返回的多为当日 00:00（日期粒度），fulltextSearch 才有时分；timeline 按
   接口原样落库。
